# Расчёт пополнения: согласованный MVP

Пользователь — менеджер закупа. Вход: выданные Excel IEK и Systeme Electric.
Выход: объяснимый проект заказа по поставщику, проверка, корректировка,
подтверждение конкретной версии, CSV/XLSX. Отправка поставщику не реализуется.

## Поток и владельцы

`Excel → adapters → Dataset → engine → Calculation → Streamlit → review → export`

- DEV A (этот проект): `replenishment/`, `tests/test_engine.py`, `tests/test_importer.py`.
- DEV B: `app.py`, оформление интерфейса и `tests/test_app.py`. Пока напарник не начал,
  предоставляется минимальный рабочий интерфейс для интеграции. Перед параллельными
  правками согласовать владельца этих файлов.
- Общий контракт: `replenishment/models.py`, владелец DEV A. Изменения согласовывать.
- Одна Python-программа, без HTTP backend, внешних API и базы данных.
- Количества считает детерминированный Python. Объяснения строятся из слагаемых.

## Агентный слой (ветка agent-integration)

Основной расчёт работает без LLM. Агентный backend подключён к UI в PR №1:
модель вызывается только по отдельной кнопке в учебном режиме. Он получает
проверенный расчёт через инструменты, а при нехватке данных backend останавливает
запрос до модели. Точный контракт: [AGENT_CONTRACT.md](AGENT_CONTRACT.md).

Агент не становится источником числовой рекомендации: количество продолжает считать
`engine.py`. Статусы `needs_data` и `invalid_data` нельзя превращать в диагноз или заказ.
Подготовка экспорта остаётся за `review.py` и требует действующего approval. Ошибка
модельного API должна давать безопасный статус недоступности, а не вымышленный ответ.
Провайдер и модель фиксируются только при реализации; секрет хранится вне Git.

## Инварианты

- Ключ товара: поставщик + точный строковый код 1С. Ведущие нули сохраняются.
- Месячные продажи и накладные не складываются: первые — основной ряд,
  вторые — подтверждение и поиск разовых операций. Несовпадения показываются.
- Исторический начальный остаток не выдаётся за актуальный. Для IEK при отсутствии
  текущего среза заказ блокируется до явного ввода менеджером.
- Ноль, пустая ячейка, отсутствие строки и неизвестный запас различаются.
- Нулевой остаток на начало месяца не доказывает дни stockout. Прокси даёт предупреждение;
  компенсация считается только для явно введённых подтверждённых дней.
- Клиентская группировка работает при наличии анонимного ID; в выданной детализации
  таких ID нет. Накладная не заменяет клиента.
- Категории — исходные коды. Их коммерческий смысл не выдумывается. Категорийный
  фильтр меняет состав расчёта; дополнительные правила категории вводит менеджер.
- Горизонт, срок поставки и разрешённые поправки видны в настройках.
- MOQ и кратность различаются. Пересчёт метров в бухты без коэффициента запрещён.
- Каждая рекомендация сохраняет исходные значения, метод, предупреждения и ссылки.
- Изменение входов или количества отменяет подтверждение. Экспорт утверждённого
  заказа доступен только после подтверждения текущей версии.

## Приёмка по ТЗ

1. Проверка влияния продаж, запасов, поставок, сезона, роста и категорий.
2. Раздельные проверки сезонного ряда и устойчивого роста, без удвоения тренда.
3. Подтверждённый stockout повышает оценку спроса; прокси не выдаётся за факт.
4. Одиночная аномалия не раздувает заказ; повторяющийся рост сохраняется.
5. Строки сгруппированы по поставщику, количество объясняется, есть экспорт.

Синтетические сценарии проверяют алгоритм, но не восполняют реальные отсутствующие
поля. Полная совместимость импорта с 1С не заявляется без спецификации 1С.

Почасовые результаты: контракт → рабочий расчёт → проверки → интеграция → демо.
Фактические результаты и оставшиеся ограничения фиксируются в STATUS.md.
